# Viewer permission foundation (PR #21; default off)

Migration `005_viewer_permissions.sql` implements only the existing-viewer portion of the merged [architecture](architecture/gateway-access-model.md). It adds a three-code client catalog (intrinsic self identity and two grantable read permissions), per-operator human entitlement/policy rows, explicit viewer grants, membership status/version and session authorization versions. The one-membership-per-user PK and viewer-only role CHECK remain unchanged. No administrator, owner, sponsor, delegation, new account, key issuance or policy-management endpoint/tool is introduced.

## Compatibility cutover — separate deployment approval required

This PR does not deploy or execute any migration on an external database. Keep both dashboard flags off and block human ingress before any separately approved 005 cutover. The current server still automatically runs migrations through its existing startup pool: reviewing/merging this PR is not authorization to restart/deploy it against staging. Runtime/migration credential separation and verification-only restricted runtime startup remain deferred prerequisites from the architecture; no Render configuration or credentials are changed here.

005 invalidates all existing authenticated dashboard sessions; anonymous pre-auth rows remain valid. It preserves user/key verifiers, operator/payment IDs, machine scopes/revocation and simulator behavior. Eligible existing memberships get exactly payment-read/status-read grants. Disabled users produce retained disabled memberships; their grants, and grants for suspended tenants, are retained revoked. Reactivation alone does not give them read rights. Later users/operators receive no automatically seeded policy or grants; missing policy denies human login/admission. No startup/login repair, role-based fallback or rerun of the recorded migration reconstructs rights.

An old application binary ignores human grants. Rollback must keep dashboard flags and human ingress disabled even if the new schema is additive. No down migration, restored old session snapshot or automatic grant reactivation is supported. The deployed feature remains simulator-only and default off.

## Admission and lock contract

The human authorization linearization point is the bounded BFF admission transaction. The validator resolves a candidate membership/operator from the token, acquires the shared pre-gate and tenant row `FOR SHARE`, and then locks user, membership, operator and active grant rows in explicit order before refreshing the session. It rechecks active status, viewer role, token/hash linkage, wall-clock idle/absolute expiry and captured user/membership/operator versions. Effective permissions are active explicit grants intersected with enabled entitlements, the client catalog and the two implemented actions. Subject-only `/auth/me` does not require either business grant, and its response remains the existing viewer DTO.

Payment list/detail require `client.payments.read`; status requires `client.status.read`. A missing business grant is 403, an invalidated session is 401, and DB/capacity failures are sanitized. All DB leases/locks are released before upstream HTTP. An admitted in-flight read may finish for its original tenant after a later withdrawal; admissions after the withdrawal commit deny. No extra human information is added to the signed loopback restriction. Its existing path/key/expected-tenant/read-only-machine checks and payment SQL predicates remain independent and mandatory.

The implementation adds a transaction-scoped advisory **pre-gate** (hash of a fixed namespace and canonical tenant UUID) before the architecture's tenant row gate. Policy admission uses shared xact locks; disposable maintenance fixtures use exclusive xact locks and `FOR UPDATE`, then sorted users → memberships → operators → grants → sessions. Defensive triggers check `pg_locks` for the current backend's matching exclusive pre-gate and refuse missing gates; they never acquire a gate after the UPDATE has locked its target. This check is not human authorization or a substitute for the ordered entry point/row gate. PostgreSQL's lock view does not distinguish session versus xact ownership; approved callers must use xact locks and proper rollback/discard. No production mutation caller is provided. Database owners can bypass these constraints; they remain outside the application threat guarantee.

Final login now locks the policy/identity before consuming the pre-auth row and rechecks password/auth version/membership under those locks. CSRF-only and cleanup paths do not acquire tenant gates after session locks. Session touching uses bounded READ COMMITTED execution, one lease, ordered locks and wall-clock expiry rechecks. Deadlocks/timeouts fail closed without automatic retry. No DB lease crosses hashing, browser interaction or loopback HTTP.

## Permanent revocation and restricted roles

Entitlement withdrawal atomically advances operator policy version, permanently revokes affected active legacy grants, advances membership versions and deletes sessions. Restoring a ceiling never inserts grants or clears a revocation. Member/user disablement retains membership rows and revokes grants; reinstatement cannot restore them. Immutable identity/source triggers reject retargeting and key-column updates; grant history references prevent deleting a membership while its history remains. Individual grant revocation also invalidates membership sessions. There is no new grant/regrant source or runtime privilege-changing route.

Restricted human-runtime credentials must have SELECT on policy/identity data and only the session/limiter metadata DML needed by existing authentication. No policy/catalog/grant insertion, entitlement changes, lifecycle mutation, evidence deletion or DDL is granted by this migration. The existing startup-owner connection is not claimed to be a deployed restricted runtime role.

PostgreSQL requires an UPDATE privilege for `SELECT ... FOR SHARE`. The tested restricted-role recipe grants UPDATE **only on immutable identity columns**: users/memberships/operators/grants `id`, and policies `operator_id`. New BEFORE UPDATE OF triggers reject every actual statement targeting these columns, including `id=id`, even for a caller holding the pre-gate. This permits row-lock admission without enabling lifecycle or policy writes. The migration installs guards but does not create roles or deploy GRANTs. Disposable tests use a dedicated NOLOGIN role, execute the real policy read/lock functions and prove that policy DML, identity updates and DDL deny. Any future restricted-role rollout must preserve these guards and independently verify grants and TLS. It must not grant broad UPDATE just to make row locking work.

Current machine API-key scopes remain independent of human permissions. A human withdrawal does not change a key hash/scope/revocation or simulator write authority. Tenant status still governs machine key authentication, including existing reactivation of non-revoked keys. No public payment business logic or idempotency code changes.

## Final grant and authentication lock audit

The only accepted grant UPDATE is active → revoked, with all revocation fields present, `revoked_at=statement_timestamp()` and the exact current operator policy version. Identity/source/creation columns remain immutable, including no-op statements targeting them. Active no-ops, partial metadata, caller-chosen historical/future timestamps or policy versions, and every UPDATE of an already-revoked row fail. Trigger-driven withdrawals use the same statement timestamp. Successful revocation still advances membership authorization version and deletes its sessions. This is not a production grant-mutation API; the ordered privileged writer contract is still mandatory.

| Path                                            | Lock/dependency order                                                                         | Why no reverse edge to policy/identity locks                                                                                                                                                                                 |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session admission                               | shared pre-gate → policy → user → membership → operator → grants → session                    | Ordered transaction releases everything before HTTP.                                                                                                                                                                         |
| Final login                                     | shared pre-gate → policy → user → membership → operator → pre-auth session → new session      | Password hashing and limiter statements finish first; the new authenticated session FK checks reference identities already held. Login never locks a session before its gate.                                                |
| CSRF refresh                                    | ordinary snapshot identity lookup, then standalone session `csrf_hash` UPDATE                 | The lookup holds no identity row locks after completion. Only the non-FK CSRF column changes; it does not run policy/session-admission logic while holding the session row.                                                  |
| Logout                                          | ordinary snapshot identity lookup, then standalone session DELETE                             | Deleting this referencing child row does not lock referenced identity rows or call policy triggers. No later query retains that session lock.                                                                                |
| Cleanup                                         | expired session rows `FOR UPDATE SKIP LOCKED` → expired limiter rows `FOR UPDATE SKIP LOCKED` | Never acquires policy/identity/grant locks. Rate-limit requests finish their standalone statements before taking authentication locks. Concurrent cleanups skip each other's rows.                                           |
| Entitlement withdrawal / member or user disable | exclusive pre-gate → policy → ordered users → memberships → operator → grants → sessions      | The controlled writer prelocks in this order before DML; trigger updates reuse these locks. Exclusive pre-gate serializes reducers and excludes admission/login. Triggers reject missing gates instead of taking gates late. |

No confirmed reverse-lock defect was found in CSRF, logout or cleanup, so their production implementations are unchanged. Deterministic tests pause the ordered writer **before session locking**, with its gate, identities and grants already locked, and require the real CSRF refresh/logout request to complete before allowing each withdrawal to finish. These would block if the session operation acquired any of those identity locks (including implicit FK locks). Cleanup is separately run while a writer holds an expired session row and must leave it intact until release, then remove it. Existing barrier/lock-observation tests cover final login and admission versus reducers in both orders. Deadlines detect a failure; arbitrary elapsed sleeps are not used to select the interleaving. This proves the tested protocol, not unrestricted owner SQL or future triggers/maintenance paths.

CSRF/logout snapshot races can return a token/success after concurrent invalidation, but cannot recreate a deleted authenticated session or restore a permission. The next identity/business read revalidates atomically. Out-of-protocol identity-changing session writes, future policy callers or additional triggers require a new lock audit.

## Test evidence and limitations

Use `npm run test:isolated -- --check` with Docker for disposable tests. Linux CI uses its guarded disposable PostgreSQL service and enables real localhost HTTPS Chromium. Native Windows CI exercises the existing DPAPI/parser and frontend tests; no Windows Docker/browser integration claim is made. No tests use Render or real credentials.

Populated-004 tests verify transactional 005 rollback, exact compatibility backfill, preserved verifiers/payments, revoked ineligible records, session cutover and retained constraints. BFF tests cover each permission independently, self identity, non-resurrection after ceiling restoration, immutable membership/history, direct SQL gate refusal, real restricted-role DML rejection, signed key-binding/tenant regressions, and deterministic admission-before-withdrawal / withdrawal-before-admission / concurrent reducer orderings. Existing expiry/password/login/search-path/browser regressions run with the new lock order and version shape. Test-owner fixture setup represents already-migrated viewers; guarded teardown deletes only synthetic evidence in the disposable DB. Neither helper is a production provisioning or mutation API.

No code here enables that maintenance surface. Administrator/subaccount/owner/branding work is still deferred; staging and production remain unaccessed.
