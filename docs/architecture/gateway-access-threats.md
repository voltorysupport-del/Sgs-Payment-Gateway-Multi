# Threat model and authorization acceptance tests

**Proposal only; tests below are not implemented or claimed passing.** See the [architecture](gateway-access-model.md) and [schema contract](gateway-access-schema.md). Tests must use disposable PostgreSQL, synthetic accounts/credentials and local HTTPS browsers. Never use real operators, payment providers or Render databases.

## 1. Assets, trust boundaries and adversaries

Protect tenant payment history, user/member identity, machine credentials/verifiers, owner authority, delegated grants, sessions, audit integrity and simulator-only safety. Untrusted inputs include every browser field/header/URL/Host, uploaded branding asset, API request, replay and stale client state. Trusted boundaries are authenticated realm validators, versioned policy evaluation, explicit server tenant context, scoped repositories and constrained database transactions. The browser and roles displayed in it are never trusted policy engines.

Model malicious restricted users, compromised client administrators, stolen/old sessions and machine keys, unauthenticated attackers, concurrent administrators, hostile domains/assets and operator error. A database superuser or compromised runtime process is outside ordinary row-predicate guarantees; use least privilege, secret custody and independent audit controls to limit/detect that compromise. Owner authority is intentionally broad, but does not excuse unscoped routes or permit secret extraction.

## 3. PR #21 acceptance — existing viewers only

These tests are implementable in the reduced foundation. Fixtures contain operators A/B, several **viewer-only** users with retained memberships, mixed payment data and existing active/revoked machine key scopes. Use populated schema 004 for the real 005 compatibility backfill. No administrator, subaccount, sponsor, owner or root-grant fixture may be persisted under 005. Controlled disposable maintenance-role helpers test withdrawal/disablement using the same source/FK/retention constraints, never a fake human administrator or test-only root bypass.

1. **Compatibility and eligibility:** eligible viewers retain exactly initial payment-read/status-read access plus intrinsic subject-only identity. Disabled users/memberships and suspended tenants have revoked cutover grant records and cannot gain rights by reactivation alone. `/me` remains compatible with the viewer DTO; self identity never implies permission to list payments. No new accounts, machine credentials, administrators or payment records are produced by the migration.
2. **Current isolation:** use A's cookie against B's known/unknown payment IDs and browser operator selectors; verify no foreign records, counts or context. Preserve the configured single-operator BFF restriction, fixed loopback route, machine read-only key checks and signed tenant/key/path binding. Continue all current payment/idempotency/simulator and Bearer scope/rotation/revocation regressions.
3. **Exact human read permissions:** withdraw payment-read from a populated viewer and retain status-read; payment list/detail deny while status succeeds. Withdraw status-read separately. Missing grants, disabled/missing ceilings, missing policy rows, unknown codes, wrong realm, malformed/revoked/expired sessions and unsupported methods fail closed. An old viewer role must not recreate compatibility rights. Repeated login or restart cannot re-run the backfill.
4. **Non-resurrection:** withdraw an entitlement while multiple viewers hold active legacy grants. Confirm ceiling, permanent grant revocation, version advancement and session invalidation commit atomically. Restore the ceiling and sign in again: revoked grants still deny. Membership/global-user disablement retains rows, revokes grants and invalidates cookies; restoring status does not regrant. Same-user replacement, tenant reassignment, deletion/recreation, ID recycling and role promotion are rejected/unavailable, not tested as supported 005 lifecycle operations.
5. **Read linearization:** barrier A commits BFF admission before withdrawal B: the admitted request may finish for its original operator only. Reverse order: admission denies. In both cases upstream independently enforces the original machine-key read-only/tenant restriction and payment SQL predicates. Revoking/changing that key during the hop retains existing denial tests. Do not pretend the existing HMAC carries human permission/version. No DB lease spans loopback HTTP; stricter upstream human revocation propagation remains deferred.
6. **Locks and failure:** use explicit gate/row barriers for admission versus withdrawal, session activity/final login versus disablement, concurrent reducers and stale version updates. Verify SHARE admission versus UPDATE policy gate and the schema §3 lock order in both orderings. Restricted-role raw policy DML must deny; row triggers must not acquire the gate after a target row lock. Inject lock timeout/deadlock/database/commit failures and verify no partial grants or automatic unsafe retry; connections recover. If the protocol cannot be proven, production mutation capability remains unavailable.
7. **Migration/rollback:** populated-004 full-transaction upgrade and injected rollback failures; concurrent migration runners; exact hashes, IDs, viewer-only CHECK, FK/index shape and revoked flags; zero root grant sources. Test fail-closed old-binary rollback with dashboard gates/ingress blocked. Session invalidation is deliberate and documented; no null-version authenticated session is trusted after cutover. Do not restore old sessions/grants from backup to undo revocation.
8. **Current browser/security regressions:** local HTTPS, two populated viewers with distinct current grants, real revocation/expiry, both BroadcastChannel modes, pending/late cookies, logout barriers, shared-cookie identity changes, stale data clearing and focus. Existing CSRF/Origin/password-rate controls, no-store/CSP and bundle/log credential scans remain intact. Run Linux and native Windows checks as applicable; do not claim a mock response proves browser cookie enforcement or runtime DB privileges.

## 4. Deferred client administrator and delegation tests

Only after a separately reviewed provenance/history schema can represent valid roots, test persisted administrators/subaccounts through real constrained creation paths. This work is **not PR #21 acceptance** and is not claimed proven by its viewer tests.

- Effective child grants are a subset of live same-tenant sponsor authority, ceiling, delegable catalog and enabled actions. Reject wildcard/unknown/platform codes, self-promotion, wrong/dead sponsor, self-reference/cycles, transitive delegation and creating/altering other administrators.
- Deterministically race grant creation against sponsor downgrade/suspension/removal, entitlement withdrawal and session invalidation. Verify transaction ordering, permanent child revocation and explicit reviewed regrant; sponsor/ceiling restoration alone cannot resurrect rights.
- Test member, invitation, audit and future key-management IDOR with real populated foreign tenants. Verify exact actor/target actions, step-up, version checks, atomic audit, single-use invitation consumption and stale issuer rejection.
- Membership replacement/reassignment tests require the future reviewed history representation; they cannot be made to pass by deleting 005 evidence or changing immutable IDs.
- Future machine-key management needs its own issuer/service-ownership lifecycle contract and tests. Current machine keys remain independent of human grants: a human downgrade alone does not revoke them, alter scopes, prevent existing simulated writes or change explicit key revocation. Do not assert that 005 imposes tenant-wide machine capabilities via human ceilings.

## 5. Deferred owner-realm and white-label tests

After owner origin/principal/provenance/MFA/recovery design is approved, create real constrained synthetic platform principals, not a client `isOwner` flag. ## 6. Deployment prerequisites and stop conditions
