# Threat model and authorization acceptance tests

**Proposal only; tests below are not implemented or claimed passing.** See the [architecture](gateway-access-model.md) and [schema contract](gateway-access-schema.md). Tests must use disposable PostgreSQL, synthetic accounts/credentials and local HTTPS browsers. Never use real operators, payment providers or Render databases.

## 1. Assets, trust boundaries and adversaries

Protect tenant payment history, user/member identity, machine credentials/verifiers, owner authority, delegated grants, sessions, audit integrity and simulator-only safety. Untrusted inputs include every browser field/header/URL/Host, uploaded branding asset, API request, replay and stale client state. Trusted boundaries are authenticated realm validators, versioned policy evaluation, explicit server tenant context, scoped repositories and constrained database transactions. The browser and roles displayed in it are never trusted policy engines.

Model malicious restricted users, compromised client administrators, stolen/old sessions and machine keys, unauthenticated attackers, concurrent administrators, hostile domains/assets and operator error. A database superuser or compromised runtime process is outside ordinary row-predicate guarantees; use least privilege, secret custody and independent audit controls to limit/detect that compromise. Owner authority is intentionally broad, but does not excuse unscoped routes or permit secret extraction.

## 3. Required negative fixture matrix

Create at least operators A and B, an owner principal with only platform-read permission, an owner without it, administrator A, administrator B, restricted users A1/A2/B1, a compatibility viewer, active/revoked read-only and read/write keys, and mixed-status payments. Give users deliberately different grant sets. Do not test tenant isolation with empty foreign tables or identical synthetic data only. Guarded fixture helpers must establish real grants/provenance, not bypass policy by editing a role string in every test.

1. **Realm isolation:** client cookie/Bearer/forged `isOwner` cannot call any owner route; owner cookie never authenticates public payment or client routes. Mixed cookies, duplicate cookie names, malformed tokens, wrong Origin, bad CSRF, GET/HEAD/OPTIONS/PATCH method changes, disabled principal and removed membership all fail closed. No state changes occur on denied methods.
2. **Tenant isolation:** run every list/detail/mutation with A's identity and B's target UUID, nested parent, query/body/header operator selector, invitation, key and audit identifier. Include uppercase UUIDs, invalid UUIDs and unknown tenants. Assert no B records or counts, no metadata writes and uniform absence semantics.
3. **Permission catalog:** A1 with payment-read can list/detail but cannot read directory/audit or delegate; A2 with status-only cannot list/detail payments. Hidden buttons do not authorize direct HTTP calls. Empty, unknown, duplicate, oversized, wildcard and platform permission lists deny. Client admin cannot alter another admin or itself through the restricted-user command.
4. **Delegation subset:** test a sponsor missing each individual requested capability; nondelegable code; unrelated/dead/suspended sponsor; wrong-tenant sponsor; self-reference/cycle; owner bootstrap forged as a client action; tenant entitlement absent. Requested grants must remain a subset at commit, not merely at form load.
5. **Deterministic races:** pause after initial auth and before transactional policy selection; downgrade/suspend/remove/reassign actor or sponsor, revoke a grant, change entitlement, invalidate session or rotate/revoke a key. Use barriers, not sleeps as race evidence. Assert exact allowed linearization for writes and documented original-tenant snapshot semantics for in-flight reads. Reverse transaction order too; test competing promotions/demotions and last-admin removal for deadlocks/timeouts/recovery.
6. **No resurrection:** remove then recreate membership, reduce then restore entitlement, suspend then reactivate sponsor/user/tenant, replace administrator and restore from a stale permission form. Old sessions and revoked grants stay unusable; only an explicit newly authorized regrant succeeds.
7. **Owner reads:** platform-read owner can access explicitly selected A and B using dedicated routes and a bounded cross-client query; read-without-permission owner cannot. Owner views include correct tenant attribution. No owner read produces payment writes, API keys, raw secrets or client impersonation. Audit failure returns no privileged data. Client requests can never reach the owner repository adapter.
8. **Machine key independence:** preserve public read/write behavior, idempotency per tenant, simulator transitions and existing rotation scope. Cookie permissions do not expand key scope. A human without represented write capabilities cannot mint a read/write key even with key management; a machine key cannot manage users/delegation. BFF binding races remain covered until replacement.
9. **Session/browser behavior:** real local HTTPS, two populated users with different permissions, two tabs/shared cookies, both BroadcastChannel modes, late login/logout/cookie responses, revoked membership/grants, failed logout and explicit reconciliation. Clear stale tables/identity and focus correctly; server denial remains authoritative despite stale UI. Owner origin cannot borrow client CSRF/cookies or vice versa. Verify Origin/host forwarding under explicitly trusted synthetic proxies, not production networks.
10. **Migration/constraints:** populated schema-004 upgrade, failure at each backfill/DDL boundary and whole-transaction rollback; concurrent runners; correct indexes/FKs; preserved password/key verifiers and revoked flags; zero auto-admins/keys; exact viewer backfill; no cross-row sponsor loopholes through approved direct administrative updates. Test altered search paths/temp-table shadowing and invoker permissions. Old application rollback must not recover revoked sessions/grants or authorize new role shapes accidentally.
11. **Audit/privileges:** sensitive mutation and audit both commit or neither does. Ordinary runtime cannot rewrite/delete/truncate audit or alter catalog/schema. Test real disposable restricted runtime and migration roles. Denied-event logger failures still deny; logs/errors/bundles contain no credential material or cross-tenant DTOs. Tenant audit reader cannot enumerate owner/other-client events. Bound event/metadata sizes and retention behavior.
12. **Availability and branding:** blocked reads, exhausted pools, connection failures, upstream disconnects, malformed/oversized owner reports and recovery after cancellation; no pool lease held across HTTP. Reject executable/foreign-tenant logo assets, remote URLs, unverified/custom owner-host claims and unapproved branding keys. Cache/view replacement must not reuse another tenant's state.

## 4. Release evidence and stop conditions

A future PR must identify implemented versus deferred permissions, exact migration compatibility and invalidation impact, focused negative/race test results, full existing payment regression results, browser coverage limits, Linux/native Windows checks, audits and redacted secret scans. Passing unit tests alone do not establish DB privilege, browser cookie, proxy or authorization safety.

Stop implementation if architecture approval is absent. Stop privileged feature enablement if owner-origin/MFA/recovery decisions, audit durability, runtime PostgreSQL TLS/least privilege, bounded query capacity or rollback semantics are unverified. Stop an operation if actor/tenant/policy/audit state is unknown. Never fall back to a global key, permissive role, disabled CSRF/TLS check or an unscoped query to get a demo working.

No future milestone may merge, deploy, provision real principals/credentials, access staging or enable real payments based only on this document. Every rollout requires independent review and explicit approval. PR #21 should prove the smallest client policy foundation while leaving the existing simulator-only read-only dashboard and public payment behavior intact.
