# Proposed schema, migration compatibility and audit design

**Documentation only.** This is a logical schema/constraint specification, not executable SQL or authorization to apply DDL. Read the [access model](gateway-access-model.md) first. Proposed filenames 005–008 are illustrative; confirm the next unused migration number at implementation time. Do not edit applied migrations 001–004.

## 1. Invariants to preserve

- Existing operator/payment/key UUIDs, unique operator codes, `payments.operator_id`, per-operator idempotency and simulator-only provider constraints remain unchanged.
- Keep `dashboard_users` and its global unique username; retain one membership per user in the initial client model. Do not add a nullable tenant/owner shortcut to it.
- Keep current SHA-256 key verifiers, revoked timestamps and read-only/read-write semantics; rotations retain scope. No migration recovers/replaces keys or provisions new credentials.
- Keep Argon2id verifiers, session token/CSRF hashes and auth version. Never backfill plaintext secrets or silently promote viewers.
- Authorization changes must not revive old sessions or permanently revoked grants when a role/status is restored.
- Client read runtime roles cannot edit membership grants. Narrowly privileged administration roles may write approved policy tables, but cannot perform DDL, edit the catalog or rewrite audit history. A compromised process holding an administration credential can bypass application policy; database/application isolation must not be overstated.

A viewer is a compatibility principal, not an unrestricted grant root. Backfill exactly the existing payment-read/status-read business grants, with migration-only `legacy_viewer` source; subject-only self access remains intrinsic to an eligible authenticated membership. For subsequent requests require active viewer plus the same explicit compatibility set and active tenant ceilings; it has no administrator/delegation powers. No ordinary endpoint can mint legacy grants. Subaccount grants require their declared active sponsor and may only contain catalog-delegable permissions. Administrator root grants will require a separately reviewed owner provenance added in 006; 005 does not supply a production bootstrap command. Tests may create explicit synthetic administrative fixtures through guarded helpers in disposable databases only.

The effective evaluator must intersect recorded grants, membership type constraints, tenant entitlement ceiling, sponsor's live authority and implemented/feature-enabled actions. A DB row or role label alone is insufficient. Maintain a deny-by-default runtime catalog rather than treating every seeded permission as implemented. Administrators cannot gain payment writes merely because a future application version adds a route.

### Atomic invalidation and downgrade rules

Extend schema-qualified SECURITY INVOKER invalidation functions with pinned `search_path = pg_catalog, public, pg_temp`; qualify all security-critical tables as in migration 004. Validate ownership, role/sponsor shape and versions on every relevant mutation. Deny moving memberships between operators: disable/remove the old membership and create a distinct one after authorization; never recycle IDs. A membership cannot be its own sponsor or sponsor an administrator. User-to-tenant reassignment must invalidate the old membership/session, not repurpose it silently.

Grant/role/sponsor/status/entitlement changes increment affected policy versions and delete affected sessions in the same transaction. A parent downgrade both removes runtime effective authority immediately and marks child grants revoked permanently. Re-enabling parent/tenant entitlements does not un-revoke grants. Entitlement reductions advance tenant version and invalidate tenant sessions; grant restoration requires explicit review. Suspension through existing operators also retains migration 004 invalidation. No new trigger changes password hashing, payment rows or key hashes.

Cross-row lifecycle predicates require controlled transactional service operations plus defensive invoker triggers; ordinary CHECK constraints cannot query other rows safely. Enumerate trigger firing and lock order before implementation, including changes performed through approved administrative tools. If any invariant cannot be enforced atomically, reject the operation rather than rely on a later cleanup. Large fanout invalidation must have bounded operational design: policy-version denial is immediate, with irreversible grant revocation completed transactionally for the initially bounded tenant size. Do not ship unbounded tenant sizes/bulk reassignment without load testing or a reviewed generation/tombstone scheme that preserves non-resurrection semantics.

### Upgrade and rollback sequence

1. Review populated-004 fixtures: several tenants, viewers, live/pre-auth/expired sessions, both machine scopes and revoked keys. Record expected hashes, memberships, payment rows and public behavior without logging secrets.
2. Run 005 through the existing per-database advisory-locked transactional runner on disposable PostgreSQL only. DDL and seeded/backfilled grants must commit together; any failure rolls back the whole migration.
3. Verify no new administrators/credentials/operators/payments, exactly preserved key/password hashes and revocation, exact viewer permissions, no platform entitlements, and required FK/CHECK/index shape.
4. Deploy-compatible application rollout must have an explicit maintenance/feature-off cutover: migrate schema additively, invalidate authenticated sessions, then enable the new validator. No mixed old/new app versions may authorize administration. Existing client payment endpoints/Bearer scopes continue unchanged while dashboard features remain off. An old binary ignores grants even if the schema is additive: before rollback or mixed-version traffic, disable both dashboard gates and block dashboard/owner ingress; verify no old auth/BFF instance accepts human requests. Revoking sessions alone is insufficient because old login code can issue new ones. Do not claim rolling authorization compatibility. Test this fail-closed rollback procedure explicitly.
5. Do not assume the current runner supports down migrations: it only applies forward numbered files. Application rollback leaves additive schema and revoked sessions/grants in place. Never restore deleted sessions or revoked grants from a snapshot to “undo” a policy reduction. Forward repair is preferred; any destructive schema rollback or loss of audit data needs separate approval/backup review.

Session invalidation is a deliberate compatibility impact requiring approval and release notes, not something already performed. Test injected errors after schema alteration, backfill and trigger replacement; no partial ledger entry or objects may remain. Test migration concurrency and original SQL error preservation.

## 3. Proposed 006 — owner realm, privileged provenance and audit enforcement

Deferred until owner-origin/MFA/recovery design is approved. Logical tables:

- `platform_users`: distinct UUID/username/verifier/status/auth version, approved MFA enrollment state and created timestamp; no operator FK or client role column. Do not copy client password hashes into owner accounts.
- `platform_sessions`: own hashed token and CSRF verifiers, required platform-user FK for authenticated rows, realm-specific expiry, password/auth/MFA version, last step-up timestamp/method, explicit anonymous/authenticated row CHECK. No client membership FK.
- `platform_login_limits`, hashed one-time `platform_enrollments` / `platform_recovery_requests`: purpose, intended principal, expiry, consumed/revoked times, authorization/approval provenance and strict single-use constraints. Recovery secrets are never audit payloads. Authenticator storage and encryption/key custody must be reviewed separately before shipping.
- `platform_permission_grants`: exact platform-only catalog FK, actor/provenance, revoked timestamp; no client grant accepted. Bootstrap only through the approved ceremony; no default or universal owner seed.
- Extend client root grant provenance with source `owner_bootstrap` and FK to the granting platform principal/approval evidence. Enforce exactly one issuer shape: legacy migration source, same-tenant administrator or platform-authorized bootstrap. Administrator role alone does not authorize arbitrary root grants. Root changes invalidate client policy/session versions and sponsored grants. Separate read versus administration DB capabilities where practical; do not claim that a shared runtime SQL login can identify the actual human actor without trusted application policy. Compromise of the single service and its privileged DB credentials remains a significant residual risk.
- Extend audit actor constraints/FKs to platform principals; do not leave unconstrained polymorphic actor IDs. Owner sessions remain separate from client tables and cannot be attached to an operator to obtain implicit client authority.

No implementation may use a generic admin boolean on existing users as a shortcut while waiting for these tables. Owner and client runtime connection roles may be separate PostgreSQL logins/pools with explicit grants in the same service. Pool budgeting must account for the current maximum of ten plus any new pools; no doubling without capacity/load review.

## 4. Proposed 007/008 — lifecycle commands and branding

Lifecycle records: hashed invitation verifier, tenant, target membership/identity, sponsor, intended grant set/version, purpose, bounded expiry, consumed/revoked timestamps; composite FKs for tenant-owned references. Idempotency records scope request fingerprints to principal/realm/operator/action, persist only sanitized result identifiers, and cannot replay credential delivery. Never put plaintext enrollment credentials or API keys in these records. Acceptance locks the invitation/policy, revalidates live authority and consumes once.

Branding: one `operator_branding` record per operator, unique `(operator_id,version)` history or explicit version counter, approved display text/palette/controlled asset ID and updated actor. Separate `operator_verified_domains` holds normalized unique hostname, verification state/hashed challenge and approval history; domain claims are never immediate routing authority. Only verified domains receive independently approved TLS/host routing. Asset references are scoped by tenant and type; no remote URL or arbitrary executable SVG/CSS/HTML fields.

These records are not required for PR #21. Exact migration boundaries may move after review; all changes remain additive with explicit data retention decisions.

## 5. Audit contract and database privilege policy

A durable audit event records: UUID, server timestamp, request/correlation ID, actor realm and constrained actor reference, target operator when applicable, exact action code, target type/ID, success/denied outcome, bounded reason code, authorization-policy version, step-up/approval reference where required, and an allowlisted change summary (permission codes/status/version, not submitted free text). Keep actor/target historical attribution when identities are disabled; use RESTRICT or immutable surrogate evidence rather than deleting history with users. Platform reads across tenants require explicit target/filter scope evidence; client audit responses never include other tenants' actors, counts or identifiers. Sensitive owner reads and audit-log reads themselves are auditable.

Successful sensitive mutations and their audit insert commit in the same transaction; audit insertion failure rolls back the operation. For denied actions there is no success transaction to append to: record a separate sanitized bounded security event after rollback, with rate controls. If that record fails, still deny the request and raise a sanitized operational alert; never allow an action because auditing is unavailable. For privileged reads, persist the required access audit before returning data; fail closed if unavailable. Avoid recursively auditing audit writes. Do not copy entire requests, response DTOs, payment payloads, connection errors, headers, cookies, password/MFA/CSRF/session/enrollment tokens or raw API keys into logs.

The ordinary application role may append allowed audit records but cannot UPDATE/DELETE/TRUNCATE them or alter their triggers. Dedicated readers project tenant/platform views under route authorization. A separate migration/retention role owns DDL and approved retention jobs. Explicitly revoke PUBLIC schema CREATE and verify no runtime role owns tables/functions or has superuser/CREATEROLE/CREATEDB/BYPASSRLS privileges before privileged routes are enabled. SECURITY INVOKER is retained; do not add SECURITY DEFINER shortcuts to bypass missing grants. Deployment role/grant changes require separate approval and disposable-role tests; none are applied here.

Application assertions cannot protect against a database owner rewriting the data or audit trail. A hash chain in the same writable DB alone does not fix that. Production needs independently controlled audit retention/export, monitoring, access review and an approved privacy/retention policy; no new logging service is required merely to approve this design.

Use explicit TLS certificate/hostname verification for runtime PostgreSQL connections, independent of the privileged CLI's checks. `src/db/pool.ts` currently relies on its connection string; neither the pool nor this document establishes deployed TLS/least privilege. Separate migration credentials from runtime credentials before privileged administration is enabled. Do not disable verification to work around internal/external hostname differences. No staging inspection or new credential collection is authorized by this plan.

RLS is optional later defense in depth, not a substitute for tenant predicates or separate owner routes. If adopted, require forced policies, non-owner runtime roles, transaction-local server-derived tenant context, reset/pool reuse tests and a separately bounded owner access path. A browser-supplied setting or an owner/BYPASSRLS runtime login is not tenant isolation. PR #21 does not introduce unreviewed RLS or session-level tenant GUCs.
