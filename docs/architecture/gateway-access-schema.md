# Proposed schema, migration compatibility and audit design

**Documentation only.** No executable SQL, runtime changes or migration execution is authorized here. [Architecture and permission matrix](gateway-access-model.md) and [phased acceptance tests](gateway-access-threats.md) are companion contracts. Migration numbers are illustrative; confirm the next unused number during the separately approved implementation. Do not edit applied migrations 001–004.

## 1. Invariants and scope

Keep existing operator/payment/key IDs, simulator-only constraints, payment tenant predicates and per-operator idempotency. Preserve machine key hashes, scopes, rotation and revocation behavior independently of human grants. Preserve password/session verifiers and intrinsic subject-only self identity.

**005 / PR #21 is existing-viewer-only.** It does not introduce persisted administrators, subaccounts, sponsor relationships, role expansion, root-grant sources, invitations or management HTTP writes. Those need a later provenance/history design. No fixture may impersonate an administrator by misusing a legacy grant or bypassing production constraints.

Keep one retained membership per user with the existing `user_id` primary key. Membership disablement is a retained row plus permanent active-grant revocation and session invalidation. Historical grants keep required membership references. Do not delete a membership to make room for another, reuse its ID, retarget its operator or promise same-user replacement under 005. Same-user replacement, tenant reassignment, multi-tenant membership and historical deletion/archive mechanics require a separate future migration. Global-user disablement must make its membership ineligible and revoke its active human grants through the controlled invalidation contract; reactivation does not restore them automatically.

For active users in active operators, backfill exactly the two current business grants. For disabled memberships/users or suspended operators at cutover, retain compatibility records as revoked with an explicit cutover reason; do not activate them. This is a deliberate conservative impact: later reactivation alone cannot activate human read rights. Intrinsic self identity requires a valid active user/membership/operator and current session; it does not provide payment/status permission.

A viewer role is never sufficient to reconstruct missing grants. Effective business permissions are active recorded grants intersected with current enabled human ceilings and implemented read/status actions. Migration history prevents re-running the backfill; restart, login, new application versions, missing-row repair and entitlement restoration must not silently seed rights. New-human onboarding and any new grant/regrant source are deferred. Existing creation/recovery paths must fail closed rather than invent 005 grants.

### Entitlement withdrawal and non-resurrection

A controlled withdrawal transaction for operator T and permission P must:

1. Acquire the exclusive tenant policy gate using §3 before other protected rows.
2. Disable ceiling P and advance T's authorization version.
3. Permanently mark **every affected active human grant** `(operator=T, permission=P)` revoked, including `legacy_viewer` compatibility grants, with reason/time/version attribution. Do not delete those records.
4. Advance affected membership versions and invalidate affected authenticated sessions in the same transaction. Conservative invalidation of all T sessions is permitted if documented and bounded.
5. Commit all changes together; failures roll back all effects. No intermediate enabled ceiling plus stronger active grant state may escape.

Restoring ceiling P does not clear any revocation or create a replacement grant. Newly authenticated viewers still lack P. A new grant requires a separately authorized future operation with reviewed provenance, validation and durable audit; it does not exist in PR #21. Withdrawals can therefore be tested in 005 without inventing administrator roots. Policy version comparison is additional defense, **not** a substitute for irreversible grant revocation.

Membership/global-user disablement similarly retains membership/grant history, revokes active human grants, advances appropriate versions and invalidates sessions. Tenant suspension still blocks all client eligibility and invalidates sessions; machine keys remain governed by existing operator status, scope and explicit key revocation. Permanently withdrawn human grants never reactivate on tenant reinstatement. Do not mutate payments or machine key scope as a side effect.

## 3. Lock protocol and fail-closed write restrictions

### Permitted entry points

005 has no dashboard policy-write route, administrator actor or production grant-issuance command. Initial catalog/policy/grant insertion occurs only in the migration transaction during the approved feature-off cutover. Subsequent withdrawal/disablement semantics may be implemented and exercised through controlled transaction helpers in verified disposable tests; production execution requires a separately reviewed maintenance entry point, authorization/audit and explicitly approved operation. A fixture maintenance database role is not a human root administrator and cannot bypass the same FK/CHECK, grant-source and revocation invariants.

Any later approved maintenance entry point must resolve an immutable target tenant, acquire the gate before issuing protected UPDATE/DELETE statements, and recheck target ownership after locking. No arbitrary SQL endpoint, session GUC, role label, browser selector or helper that silently opens an independent pooled transaction may substitute for this entry point. Missing gate/unknown policy state denies access. PR #21 does not authorize an unrestricted maintenance CLI.

### Acquisition order and modes

Use bounded READ COMMITTED transactions. For admission, acquire the tenant policy row **FOR SHARE** first; for withdrawal/disablement, **FOR UPDATE** first. The exclusive gate serializes policy writes; shared admission holds a stable human-policy decision until its commit. Resolve tenant from current membership before locking, then recheck unchanged membership/tenant identity under the gate; mismatch denies rather than following a moved row.

After the gate, acquire locks in this order: affected users in UUID order; affected memberships in UUID order; operator rows in UUID order; grants in stable membership/code/ID order; authenticated sessions in token-hash order. Admission uses SHARE locks for identity rows and UPDATE for its own last-activity/session refresh. A policy reducer uses UPDATE locks on rows it changes. Acquire individual classes explicitly in this order; a multi-table `FOR SHARE OF ...` join must not be assumed to guarantee row-mark order. Whole-tenant operations enumerate bounded affected rows after taking the gate. Operations spanning tenants are not in 005; later designs must order gates by tenant UUID before any subordinate locks.

The current `touchDashboardSession` locks identity rows before the session (`src/dashboard/sessions.ts:32–55`) and the login transaction consumes pre-auth state before final identity selection (`src/dashboard/routes.ts:211–228`). Before gate-protected reducers can coexist with new admission, refactor the relevant bounded validation/final-login transaction to follow the common gate/identity/session order. Keep pre-auth token single-use and final password/membership rechecks. Initial password lookup/Argon2 work holds no tenant gate; final login authorization acquires it before identity/session changes. `/me` and BFF admission must use the new validator consistently. Do not open a second pool connection to touch sessions while holding the first connection's gate. Anonymous CSRF/cleanup operations must not acquire a tenant gate after taking a session row and then call back into policy validation; review those paths explicitly. No DB lock/lease spans loopback HTTP, browser interaction, hashing or provider I/O.

### Triggers, direct SQL and failure behavior

Retain schema-qualified SECURITY INVOKER functions and pinned `pg_catalog, public, pg_temp` search paths. Existing row triggers in migration 004 run after their target row has already been locked by the UPDATE statement. Neither BEFORE ROW nor AFTER ROW triggers can retroactively make a tenant gate the first lock. Do not put gate acquisition inside such a trigger and claim correct ordering. A caller-set GUC is not proof that the caller holds the required lock or has human authority.

The enforceable initial boundary is restricted DML: runtime human-read roles cannot INSERT/UPDATE/DELETE grants or entitlements, alter membership tenant/role/status, or change user/operator lifecycle policy. Catalog and legacy grant-source creation remain migration-only. Non-policy session/limiter metadata writes receive only the narrowly needed grants; public payment writes remain under their existing role/scope behavior. Approved maintenance/migration credentials are separate, unavailable to browser routes, and only used through reviewed entry points; a database owner/superuser can bypass these controls and is outside the application threat guarantee.

Defensive triggers validate immutable tenant/ID/source fields, prevent clearing revocation and perform compatible invalidation; they must not be relied on to authorize an arbitrary privileged SQL caller. Direct lifecycle/policy SQL is unsupported unless its approved entry point follows the protocol. Where runtime grants/column privileges and safe triggers cannot reliably reject a conflicting legacy write path, that mutation capability stays unavailable: deny it and defer enablement until the path is redesigned and concurrency-tested. This applies to privileged tools as well as HTTP handlers. Do not fix safety by weakening constraints or adding SECURITY DEFINER bypasses.

Bound pool acquisition, statement execution, lock waits and total transaction leases using reviewed existing patterns. On deadlock, lock timeout, serialization/database error or uncertain commit, roll back/discard as needed and return a sanitized failure. Do not swallow SQL errors, treat partial work as success, or automatically retry a non-idempotent policy mutation. Only an explicitly reviewed operation may reconcile an ambiguous outcome from durable versions/results. Shared-gate acquisition failure does not fall back to unchecked reads.

Deterministic tests must cover: admission gate first versus withdrawal first; reducer waiting on an active admission; identity/session refresh versus disablement; final login versus withdrawal; direct disallowed DML; two concurrent reducers; stale version forms; timeout/deadlock cleanup and subsequent connection reuse. Use explicit barriers and PostgreSQL lock observations in disposable infrastructure, not sleep-only evidence. Test both transaction orderings. Until the common protocol is proven, no gate-protected production mutation capability is enabled.

## 4. Upgrade, rollback and runtime database roles

The current server creates one pool and calls `runMigrations(pool)` before listening (`src/server.ts:41–45`). It is **not already** separated into migration and least-privilege runtime roles. Do not change that source in this documentation PR or claim deployed privilege/TLS evidence.

Before production least-privilege deployment, implement a separately reviewed migration execution path using dedicated migration credentials, then start the application with restricted runtime credentials. The runtime path must only verify schema compatibility, not execute DDL, create migration-ledger tables, backfill grants or “repair” missing policy rows. A missing/unreadable ledger, missing required migration or constraints/catalog version, incompatible newer schema, missing privileges, or unverifiable compatibility must fail startup before binding the listener. Define an explicit supported schema/catalog version range, not simply “latest number >= required.” Deployment must never fall back to migration credentials, permissive roles, disabled TLS or old authorization logic. No such runner/startup change is implemented by PR #20; it is a prerequisite for the corresponding restricted-role deployment, separately scoped/reviewed alongside or after PR #21.

Migration 005 implementation acceptance:

1. Use populated schema-004 disposable fixtures with active/disabled users, active/suspended tenants, live/expired/pre-auth sessions, payments and both active/revoked machine scopes. Record expected verifier equality without printing secrets.
2. Verify migration-only bootstrap/backfill, identity preservation, viewer-only CHECK, retained membership references, exact eligible compatibility grants and revoked ineligible records. No administrator, sponsor, key, account or payment is created. Inject failure after each DDL/backfill boundary and verify whole-transaction rollback/ledger behavior with the existing advisory-locked runner.
3. Cut over with both dashboard gates and dashboard/owner ingress disabled before migration. Invalidate authenticated sessions, install the consistent validator, and verify compatibility before any separately approved enablement. No mixed old/new human authorization traffic is safe: old binaries ignore grants and can create fresh sessions.
4. Old-binary rollback leaves additive schema and revoked history in place but keeps dashboard/owner routes unavailable. Test that ingress and gates deny all human requests; session deletion alone is insufficient. Public Bearer behavior remains unchanged. No automatic down migration or resurrection from backups; forward repair is preferred.
5. Test session version shape/expiry/invalidation, immutable ownership, policy reads/withdrawals under §3 and post-failure recovery. A future role split must test actual restricted runtime/migration roles and startup verification, not rely only on table-owner test connections.

Runtime TLS must explicitly verify certificate and hostname. `src/db/pool.ts` currently derives TLS behavior from its connection string; CLI preflight does not prove runtime policy. Verify no runtime DDL ownership, superuser/CREATEDB/CREATEROLE/BYPASSRLS or PUBLIC schema CREATE before privileged feature deployment. Role/grant/TLS changes need separate approval; none are executed here. Keep runtime and migration credentials private and separate. Optional future RLS is defense in depth, not a replacement for authenticated tenant predicates; no unreviewed tenant GUCs or RLS bypasses are introduced in PR #21.

## 5. Deferred provenance, membership history and privileged lifecycle

A separate future schema must define valid administrator root-grant provenance **before** persisting administrators/subaccounts or testing database-backed delegation. 005 has only legacy viewer grants: do not fabricate an administrator using that source, create circular administrator issuers, seed a test-only root code into production constraints or bypass those constraints in fixtures. Pure, explicitly hypothetical delegation evaluator tests may be designed later, but PR #21 does not claim persisted delegation correctness.

That later schema must resolve membership history before replacement/reassignment: for example separate current membership from immutable history or a reviewed one-active-membership representation. This document does not select or implement that migration. Existing retained IDs and their grant/audit attribution cannot be recycled or retargeted.

Owner principals, sessions, MFA, enrollment/recovery and platform grant tables are deferred, with separate realm verifiers, host-only cookies/origin, shorter bounded sessions and target/action-bound approval evidence. Root grants must reference valid owner/bootstrap authorization, not an ungrounded client role. Owner and client grant sources must enforce exact issuer shapes and realm/tenant ownership through constraints plus live policy. No default owner or administrator account is seeded.

Only after provenance and audit controls are approved may invitations, sponsor/delegation changes, root replacement, new viewer grants or regrants be enabled. Invitation tokens are hashed, expiring, single-use and bound to intended tenant, identity, issuer authority and grant version. Administrative idempotency stores only sanitized identifiers/fingerprints, never passwords or raw credentials. Future client key-management lifecycle is separately reviewed: current machine key scopes and revocation remain independent of these human records.

## 6. Deferred audit and branding controls

The future durable audit schema must have constrained actor/provenance references, target tenant/resource, exact action, outcome/reason, server timestamp, request correlation, policy/step-up/approval versions and bounded allowlisted change summaries. Successful sensitive changes and their audit insert commit atomically; mandatory privileged-read audit must persist before returning data. Audit failure denies the operation. Denial-event logging after rollback is bounded; its failure never permits the denied action. No raw cookies, tokens, headers, keys, passwords or whole payment/request payloads enter audit metadata.

Runtime audit appenders must not UPDATE/DELETE/TRUNCATE history or alter its triggers; use separate reader projections and migration/retention roles. Database-owner/runtime-process compromise is a residual risk, not solved by a hash chain in the same database. Independent retention/export, monitoring and privacy/retention decisions remain production prerequisites. PR #21 introduces no production sensitive management operation lacking durable audit; until an audited entry point is reviewed, withdrawal/disablement reducers are exercised only in disposable tests and no production mutation tool is enabled.

Future tenant branding uses approved text/palette tokens and controlled tenant-owned asset IDs, not arbitrary HTML/CSS/JS/remote URLs. Domain ownership and TLS are independently verified before host mapping. Host selects presentation, never authority; authenticated operator/domain mismatch fails closed. Owner hostnames are reserved. Cookies stay host-only, without URL-based session transport or wildcard domains. Branding/assets/cache keys include authoritative tenant/version; cross-tenant data caches are forbidden. All branding/lifecycle migration numbers remain illustrative and are outside 005.
